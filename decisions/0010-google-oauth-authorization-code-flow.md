# 0010. Google OAuth via the Authorization Code flow, not ID-token verification

> **In todo-app-py:** The same flow, cookie and error codes, in `api/app/routers/auth_google.py`. The two HTTPS calls to Google use `httpx` (already a dependency) instead of Go's `net/http`, and still no OAuth/JWT library. The rest of this record is kept as written for todo-app (Go).

## Context
The user wants "Sign in with Google" as an additional login option on the regular login screen (not `/admin`), auto-linking to an existing password account when the Google-verified email matches one. This is the first feature to talk to an external service, and the first to need a real secret (a Google OAuth client secret) passed into the app.

## Decision
Use the classic server-side **OAuth 2.0 Authorization Code flow**: the browser is redirected to Google's consent screen, Google redirects back with a `code`, and the `api` service exchanges that code for an access token via `POST https://oauth2.googleapis.com/token`, then fetches the profile via `GET https://openidconnect.googleapis.com/v1/userinfo`. Both are plain stdlib `net/http`/`encoding/json` calls — no new Go dependency, keeping `go.mod` at zero entries like every other package in `api/`.

This app already hand-rolls PBKDF2 (`0002`) and its own HMAC token format (`0003`) rather than pull in crypto libraries — but both of those are for primitives Go's stdlib genuinely lacks, and for tokens *this app itself* mints and controls the shape of. Verifying a Google-issued ID token would mean hand-rolling RS256 signature verification and JWKS key rotation for a third party's token format, which is real, avoidable cryptographic work with no equivalent payoff here: Google's own servers already do that verification for us when we exchange the code server-to-server over TLS. The Authorization Code flow gets the same security guarantee (the account is proven to belong to whoever is signed into that Google session) for a fraction of the code.

The OAuth CSRF `state` value is 32 bytes of `crypto/rand` randomness held in a short-lived (5 minute), `HttpOnly`, `SameSite=Lax` cookie — compared byte-for-byte against the query param Google echoes back. It carries no claims, so unlike this app's own auth tokens it is not HMAC-signed with the app secret; its own unguessability plus the short cookie TTL is sufficient to defeat replay/CSRF.

The redirect URI is anchored at the Vite origin, `http://localhost:5173/api/auth/google/callback`, not the `api` container's directly-published `:8080`. `decisions/0009` establishes that the browser only ever talks to Vite's dev server, which proxies `/api/*` internally — introducing a second directly-exposed entry point for OAuth callbacks would break that single-origin invariant for no benefit, since Vite's proxy already forwards the state cookie transparently.

`docker-compose.yml`'s `api` service now reads `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` via Compose's native `${VAR}` interpolation (which auto-reads a `.env` file in the project root) — the first real secret this app has needed passed in this way. Every other env var in that file was previously a hardcoded literal. `.env` was already gitignored even though unused before this.

## Alternatives considered
- **Google Identity Services "ID token" flow** (the client-side `<script src="https://accounts.google.com/gsi/client">` button that returns a signed ID token directly to the frontend): would require the backend to verify an RS256-signed JWT against Google's rotating JWKS, entirely new crypto surface area for a token type this app doesn't otherwise use. Rejected in favor of letting Google's servers do that verification during the code exchange instead.
- **`golang.org/x/oauth2`**: would handle the flow's HTTP plumbing for us, but adds the first external dependency to `api/go.mod`, breaking the zero-dependency pattern every other package in this app follows.
- **Signing the CSRF `state` value with the app's HMAC secret** (reusing `auth.Mint`/`auth.Verify`): unnecessary — `Claims` carries user identity and expiry for actual auth tokens; `state` here is a one-time, cookie-scoped nonce with no identity to authenticate, so plain randomness is sufficient and simpler.

## Consequences
- New outbound-network failure modes at login time that don't exist for password login: Google's token/userinfo endpoints being unreachable or erroring surface as `google_exchange_failed`/`google_userinfo_failed`, redirecting back to the login screen with a generic message rather than failing silently.
- A user whose account was created via Google sign-in has no password (`PasswordHash`/`Salt` are empty) — `Login` was updated so a password attempt against such an account returns the same generic `invalid_credentials` as a nonexistent email, never revealing that the account exists but has no password set.
- Google sign-in works at `http://localhost:5173` out of the box once a Client ID/Secret are configured, but **not** automatically through an ngrok tunnel session (`decisions/0009`): ngrok's free tier issues a new random subdomain each run, and Google requires an exact, pre-registered redirect URI — there's no dynamic-URI support to exploit here. Using Google sign-in through ngrok would require either a paid ngrok reserved domain or registering that session's URL in Google Cloud Console each time; out of scope for now.
- Setting up Google sign-in requires the user to create credentials in Google Cloud Console themselves (documented in `README.md`) — this can't be done on their behalf. If `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are left blank, the "Sign in with Google" button still renders, but clicking it redirects to `/api/auth/google/login`, which responds `503 google_oauth_not_configured` instead of reaching Google.
